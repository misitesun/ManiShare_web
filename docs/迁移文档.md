## 2. “完全使用 Next.js”的完成定义

迁移完成必须同时满足以下条件：

1. `pnpm run dev` 只启动 Next.js，`pnpm run build` 只生成 Next.js production 静态产物。
2. 所有 23 个现有路由契约均由 `src/app` 文件路由承载；动态路径全部通过 `generateStaticParams()` 枚举。
3. 不再存在 `RouterProvider`、`createBrowserRouter`、`react-router-dom`、`src/main.tsx`、根 `index.html` 或 `vite.config.ts`。
4. 不再存在 `import.meta.env`、`VITE_*`、`@vitejs/plugin-react`、`@tailwindcss/vite` 或 Vite 专用类型。
5. `AppLayout` 使用 `children`，不再使用 `Outlet`；导航、参数、查询参数和错误边界全部采用 Next App Router 语义。
6. `src/app` 只放 Next 路由、布局、Metadata 和框架适配，不承载页面业务；FSD 仍遵守 `app → pages → widgets → features → entities → shared`。
7. `dist/staging`、`dist/production`、`dist/electron` 与 `release` 的公共产物契约保持明确，Electron 能直接加载 production 静态导出。
8. Web 与 Electron 均无 hydration、CSP、静态资源 404 或动态深链错误。
9. Vite 与 React Router 的直接依赖、配置、脚本、现行文档指令和 lint 规则在同一切换批次中移除或改写，不留下“默认走 Next、部分工具仍走 Vite”的状态。
10. 静态导出完整保留客户端导航所需的 RSC 数据；Web 与 Electron 的站内跳转和预取不因数据缺失退化为整页加载。
11. 干净检出可生成 Next 类型并执行严格类型检查；四个团队 Skills 和实际执行的 lint/CI 均采用迁移后的目录与框架契约。

这里的“完全使用 Next.js”指框架、路由和构建入口全部切换到 Next.js；首期静态导出仍不等同于启用 SSR、ISR 或 Server Actions。

零残留检查针对现行源码、配置、命令和有效规则，不要求从迁移历史或旧 ADR 中抹去框架名称，也不将仍有真实消费者的传递工具依赖误判为 Vite 入口。旧 ADR 的替代关系按第 20.4 节记录。

## 3. 目标与非目标

### 3.1 目标

1. 使用 Next App Router 替换 Vite SPA 和 React Router。
2. 为每个可达路由生成独立 HTML，并建立 Metadata、robots、sitemap 与 canonical 的明确边界。
3. 保留现有 React、TypeScript、Tailwind CSS 4、FSD、主题、i18n 基础、动画和共享 UI，不借迁移重做业务页面。
4. 保留同一套语义 DOM 和 mobile-first 响应式实现，继续支持 PC、平板、H5 与 Electron。
5. 让路由参数、静态资源、环境变量、Electron 协议和 CSP 成为可测试的公共契约。
6. 为未来 SSR/ISR 留出升级路径，但不提前引入当前产品不需要的服务端业务。

### 3.2 非目标

- 不在本次迁移中重设页面视觉、改写已确认交互或虚构接口数据。
- 不接入 Server Actions、请求时 Route Handlers、服务端会话、数据库或新认证方案。
- 不把个人资料、笔记、学习进度、AI 对话和收益页面开放给搜索引擎。
- 不全量把 `<img>` 替换为 `next/image`；先完成兼容迁移，再按真实收益单独优化。
- 不启用 PWA、manifest、Service Worker 或离线缓存。
- 不为迁移建立长期 Router 抽象层、兼容重导出或双套页面目录。
- 不在 Electron 内启动常驻 Next.js server。

### 4.3 已知的硬阻塞

不能采用“根目录 `app/` + 保留 `src/pages/`”的旧方案。Next.js 会分别发现根 `app` 和 `src/pages`，并要求两者位于同一父目录，否则构建直接失败。目标结构必须先消除 `src/pages` 这个框架保留目录名。

## 5. 目标架构

### 5.1 目录结构

```text
src/
├── app/                              # Next App Router，框架适配层
│   ├── layout.tsx                    # html/body、根 Metadata、全局 CSS
│   ├── not-found.tsx
│   ├── global-error.tsx
│   ├── robots.ts
│   ├── sitemap.ts
│   ├── _providers/                   # Next 专用的 Client Provider 桥
│   ├── (shell)/
│   │   ├── layout.tsx                # 装配 AppLayout(children)
│   │   ├── loading.tsx
│   │   ├── error.tsx
│   │   ├── page.tsx                  # /
│   │   ├── ai-tutor/...
│   │   ├── awakening/...
│   │   └── ...
│   └── (standalone)/
│       └── login/page.tsx
└── fsd/
    ├── app/                           # 导航配置、Provider、全局样式等 FSD 应用装配
    ├── pages/                         # 现有业务 page slices
    ├── widgets/
    ├── features/
    ├── entities/
    └── shared/

electron/                              # 安全桌面薄壳
scripts/                               # 环境、构建整理、静态预览、Electron dev
dist/
├── staging/
├── production/
└── electron/
```

约束：

- `src/app` 是 Next 约定目录，也是最外层应用装配；可以依赖 `src/fsd/app`、`pages` 及更低层。
- `src/app/**/page.tsx` 保持薄层，只解析 Next 参数、设置 Metadata、注入路径/数据并组合 page 公共入口。
- FSD 内部继续执行 `app → pages → widgets → features → entities → shared`；除 `app` 和 `shared` 外，同层 slice 不互相依赖。
- 路由适配层不得深层导入业务实现；所需页面组件和静态参数枚举器必须从 slice 根 `index.ts` 导出。
- 删除原 `src/fsd/app/router`；Next 文件路由是唯一 Router owner。
- 使用单一明确别名（建议 `@fsd/* -> src/fsd/*`）或可读相对路径，不建立多套同义 alias。
- 全局样式移动到 `src/fsd/app/styles/index.css` 后，其 Tailwind `source()` 必须继续覆盖整个 `src`，不能遗漏 `src/app` 中的字面量 class。

### 5.2 首期渲染与部署模式

`next.config.ts` 首期采用：

```ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
    output: 'export',
    trailingSlash: true,
}

export default nextConfig
```

静态导出意味着：

- 构建时为每个已知路由生成 HTML，加载后继续由 React 水合并进行客户端导航。
- 可以使用 Server Component 作为构建时路由适配层，也可以使用 Client Component 承载交互。
- 不支持请求时 SSR、ISR、Server Actions、依赖请求的 Middleware/Proxy、rewrites、redirects、headers、默认图片优化或运行时 API 代理。
- 不允许把开发服务器可用误认为静态 production 可用；所有能力必须以导出产物和 Electron 为最终验证对象。
- `next start` 不用于 `output: 'export'`。production-like 验证统一使用 `pnpm run preview` 启动项目自有静态预览脚本。

如果未来确实需要 SSR/ISR，必须新建 ADR，明确 Web Next Server 部署、缓存、认证与成本，并为 Electron 保留独立静态客户端产物；不得直接删除 Electron 离线加载能力。

### 5.3 Server / Client Component 边界

- `layout.tsx`、`page.tsx` 默认保持 Server Component；Metadata 和 `generateStaticParams()` 保持构建时/服务端入口。
- FSD 页面只有在真实使用 Hook、Context、事件处理、Storage、DOM、GSAP、WebGL 或浏览器观察器时才声明 `'use client'`。
- 不把 `'use client'` 放到根 layout，也不为追求“Server Component 数量”拆碎现有稳定业务组件。
- 动态路由由薄 `page.tsx` `await params` 后把已校验字符串作为 props 传给 FSD page，优先移除业务页面中的 `useParams()`。
- 可变查询状态继续由 Client Component 的 `useSearchParams()` 管理，并置于最近的 `Suspense` 边界内，避免静态预渲染失败。
- `usePathname()`、`useRouter()` 只留在实际拥有导航交互的 Client Component；普通链接使用 `next/link`。
- 服务端与客户端首次渲染必须一致。不能在 render 或模块顶层读取视口、Storage、`window`、`document`、Portal target 或随机值。
- 主题默认 dark 的首屏必须确定；持久化主题的 pre-hydration bootstrap 由 `shared/theme` 唯一拥有，并纳入 CSP 技术验证，页面不得复制脚本。

跨边界与公共入口规则：

- Server Component 传给 Client Component 的 props 必须可由 React 序列化。本项目路径注入使用字符串、已校验 ID 或链接数据；普通函数、闭包和浏览器对象不得跨边界传递。
- 现有交互页若需在用户选择后构造 URL，由 `src/fsd/app` 中命名明确的 Client 装配组件导入路径函数和 page 根入口，再在同一客户端模块图内注入回调。Server `page.tsx` 只向该装配组件传可序列化参数；不新增第二个 Router。
- 固定链接或构建时可确定的链接优先在 Server adapter 中构造成字符串后传入，避免为静态数据增加 Client 装配组件。不得为传递函数把根 layout/page 全部改成 Client，也不得用 `'use server'` 绕过静态导出约束。
- 同时导出页面 UI 与静态参数枚举器的 slice 根 `index.ts` 保持无 `'use client'` 的公共入口；只在实际 Client UI 入口声明指令。枚举器及其传递依赖保持构建时可执行，不导入 Hook、Storage 或浏览器初始化模块。
- Server adapter 仍从 slice 根入口读取枚举器；不能为避开边界问题改成跨模块深层导入。混合导出的合法性通过真实 Next 构建验证，不能仅靠 TypeScript 通过判断。

### 5.4 React 工程约束

- 路由级代码分割由 App Router 自然提供，不继续保留 React Router 的 `lazy()` 装配，也不为小组件机械 `dynamic()`。
- State 只保存最小源状态；可推导数据在 render 中推导，不为迁移增加同步 Effect。
- 浏览器监听、计时器、Observer、Object URL、GSAP 与 WebGL 必须保持成对清理。
- 同一语义 DOM 继续覆盖 H5、平板、PC 与 Electron；宽度差异交给 CSS，不在 Client Effect 中维护布局断点。
- `next/link`、`next/navigation` 可以由真实导航 UI owner 使用；不要为掩盖迁移建立永久的伪 Router API。

### 6.2 路径公共 API

`src/fsd/app/config/routes.ts` 不再保存 React Router 的 `:param` 模板供 `generatePath()` 使用，改为：

- 固定路由导出只读字符串。
- 动态路由导出带明确参数的构造函数。
- 每个路径参数在同一公共能力中执行非空校验和 `encodeURIComponent`。
- 查询参数通过 `URLSearchParams` 构造，不手工拼接未经编码的外部值。
- 页面不反向导入 FSD app 层。Server adapter 只注入可序列化路径数据；需要路径构造函数的 Client page 按第 5.3 节由 FSD app Client 装配组件注入。

动态路径示意：

```ts
export function createAiTutorChatPath(mentorId: string, sceneId: string): string {
    return `/ai-tutor/mentors/${encodePathSegment(mentorId)}/scenes/${encodePathSegment(sceneId)}/`
}
```

具体命名以实施时的 app config README 为准；同一条路径只能有一个公共构造入口。

### 6.3 静态参数公共 API

以下动态路由必须实现 `generateStaticParams()`，并把参数来源放在真实数据 owner 的根公共入口：

| 动态路由 | 参数来源 | 当前预期数量 |
| --- | --- | ---: |
| AI 导师聊天 | `pages/ai-tutor` 导出的 mentor/scene 参数枚举器 | 4 × 8 = 32 |
| 言灵觉醒课程 | `pages/awakening` 导出的可达详情参数枚举器 | 2 |
| 外语课程详情 | `pages/foreign-language-guide` 导出的已支持详情参数枚举器 | 1 |
| 课程包笔记 | `entities/notebook` 根入口 | 24 |
| 章节笔记 | `entities/notebook` 按课程包生成章节 | 24 × 8 = 192 |

当前固定路由 18 个，加上 251 个动态实例，预期生成 269 个业务 HTML 路由，另有 404 与 Metadata 文件。测试应从模型计算期望集合，不复制一份 ID 常量；基线数量变化必须能追溯到模型或可达链接变化。

`generateStaticParams()` 返回经过校验的原始领域 ID，由 Next 负责生成 URL；不要把已执行 `encodeURIComponent` 的值传给它。只有导航路径构造函数负责 segment 编码，测试需验证两者指向同一组路由。

每个动态 segment 同时设置并验证未知参数行为。静态导出不能在发布后生成新参数；真实后端开始返回构建时未知 ID 时，必须选择重新构建、改变 URL/客户端数据策略，或通过 ADR 升级 Web 部署模式。

| 当前 API | Next 目标 |
| --- | --- |
| `Link` | `next/link` |

| `useNavigate` | `useRouter` |

迁移完成后，以源码契约阻断任何新增 `react-router-dom` 导入。

### 6.5 查询参数与未知路由

- 保留现有 `q`、`view=course-packages`、`view=courses`、导师/场景恢复等查询语义。
- 使用 `useSearchParams()` 的静态页必须有局部 `Suspense`，不能通过把整个 root layout 改成 Client Component 规避构建错误。
- 当前未知路径会重定向首页。标准 404 更利于 SEO 与调试，但属于产品行为变化；切换前按第 17 节确认。未确认前，必须在 `404.html`/`not-found.tsx` 中显式保留现有回首页行为，不能依赖旧 SPA fallback 偶然实现。

### 6.6 导航状态、滚动与预取

迁移前在 `widgets/app-layout`、笔记页和 AI 导师页记录可观察行为，迁移后逐项对照：

| 场景 | 实施与验收要求 |
| --- | --- |
| 导航激活 | 匹配前统一处理 pathname 的尾斜杠，根 `/` 保持不变；精确匹配与完整 segment 前缀匹配分开，避免 `/profile` 与 `/profile-other` 混淆；标题、active class 和 `aria-current` 一致 |
| URL 规范化 | 路径构造器、导出目录、canonical 与 sitemap 统一采用 `trailingSlash: true` 语义；无尾斜杠入口能按静态托管/协议契约到达同一页面，不能出现刷新后高亮丢失 |
| 同页查询切换 | 保留无关 query；笔记页签沿用 replace 语义，默认保持当前位置，必要时显式使用 `scroll: false`；不要把筛选/页签操作变为新的业务导航 |
| 返回与直达 | 验证 `view=course-packages`、`view=courses`、`mentor`、`scene`、搜索 `q` 的编码与恢复；显式父级返回链接继续支持直接访问子页，不依赖未知历史 |
| 本地状态 | 记录并验证返回、重新进入、切换动态 ID 时选择、分页、弹窗与临时输入的保留/重置；不得因 App Router 复用组件就默认与旧行为等价，也不统一加 key 强制重挂载 |
| 滚动容器 | AppLayout 当前滚动发生在壳层内的 `overflow-y-auto` 容器，需分别验收跨页、同页查询、前进/返回和聊天内部滚动；不能只检查 `window.scrollY`，先对照基线再决定局部修复 |
| 预取 | 在 production 静态预览与 Electron 中检查 Link 进入视口、悬停和点击时的 RSC/chunk 请求；记录是否保留默认预取或对有证据的具体入口关闭，不全局机械禁用 |

Next 路由预取与真实业务 API 请求分开记录。路由资源预取不构成新增后端请求的授权；请求次数验收不得把二者混为一类。客户端导航必须检查是否意外产生新的 document 请求，防止整页加载掩盖静态导航数据失败。

## 7. Provider、主题与浏览器边界

根 layout 只输出确定性 HTML。Next 专用 Client Provider 桥负责组合现有能力：

- `ThemeProvider`；
- i18n 初始化与现有语言切换基础；
- PWA 安装生命周期预留；
- 未来确有全局作用域的 Client Provider。

迁移检查范围：

- `window`、`document`、Storage、Clipboard、Portal；
- `ResizeObserver`、`IntersectionObserver` 与媒体查询；
- GSAP、View Transition、OGL/WebGL 与 reduced-motion；
- Object URL、事件监听、计时器和异步清理；
- 首屏主题、语言和响应式 DOM 的水合一致性。

规则：

- 模块顶层不得访问仅浏览器存在的 API。
- 主题和语言不能让服务端与客户端第一次 render 产生不同节点树。
- Portal target 在挂载后解析；动画、Observer 和 WebGL 在 Effect/既有封装中启动并清理。
- 不使用 `dynamic(..., { ssr: false })` 作为通用修复。只有确认某个页面私有重型视觉无法预渲染且客户端占位稳定时才局部使用。
- 主题切换继续遵守 `docs/compatibility/theme-transition.md`；Next 迁移不能删除 reduced-motion 与直接切换 fallback。

## 8. 静态资源迁移

Next 的位图静态 import 返回含 `src`、宽高等信息的对象，Vite 返回 URL 字符串。当前 97 条位图 import 中，多处直接写入 `imageSource: string` 或 `<img src={asset}>`，必须显式迁移。

首期策略：

1. 保留业务资源在所属 FSD slice 的 `assets/`，不为省事全部移动到 `public/`。
2. 现有 `<img>` 默认继续使用；位图 import 在消费边界使用 `asset.src`。
3. 模型字段继续保持普通 URL 字符串时，在模型创建处存入 `asset.src`，不让 `StaticImageData` 扩散进领域/UI 公共类型。
4. SVG、CSS 背景、OGL texture 和动态 URL 分别做构建 PoC；不能假设所有扩展名与 Vite 行为相同。
5. 只有固定 URL、Metadata 文件或必须被外部直接访问的资源进入 `public/`。
6. 首期不批量改用 `next/image`。若单独采用，在静态导出下必须配置 `unoptimized` 或已验证的自定义 loader，并复测尺寸、布局和 Electron 协议。
7. 为资源迁移补静态检查或构建断言，确保导出 HTML、CSS 和 JS 不引用 Vite `/assets/*` 旧路径。

资源迁移完成后重新统计 216 条资源导入和 110 个 `<img>` 使用点，逐项说明未迁移项为何与 Next 兼容。

## 9. Tailwind、样式与响应式

- 移除 `@tailwindcss/vite`，使用 Tailwind CSS 4 的 PostCSS 接入。
- `src/fsd/app/styles/index.css` 仍是唯一全局 CSS 入口，只在 `src/app/layout.tsx` 导入一次。
- 移动后修正 `source()` 相对路径，使扫描范围覆盖整个 `src`，但不包含 docs、scripts 和测试 fixture。
- 主题原始颜色仍只存在于全局语义 token；业务组件不新增硬编码色或 `dark:`/`light:` 分支。
- 保留 mobile-first：默认 H5、`md` 平板、`xl` PC/Electron 和既有 ≥1920px 规则。
- 不用服务端 UA 判断布局，不使用根字号、`vw` 或整页缩放，不复制 desktop/mobile DOM。
- Next route adapter 中若出现 Tailwind class，也必须是完整字面量并纳入源码契约扫描。

迁移不改变既有页面的版心、网格和语义字号契约。出现视觉差异时优先修复构建、CSS 顺序或水合问题，不借机修改设计。

## 10. 环境与 API 开发策略

### 10.1 环境变量映射

| 当前变量 | Next 目标 | 说明 |
| --- | --- | --- |
| `VITE_APP_NAME` | `NEXT_PUBLIC_APP_NAME` | 浏览器可见 |
| `VITE_APP_DESCRIPTION` | `APP_DESCRIPTION` | 仅构建时用于 Metadata 默认描述 |
| `VITE_ROBOTS` | `ROBOTS_POLICY` | 仅构建时使用，默认保持 noindex |
| `VITE_API_BASE_URL` | `NEXT_PUBLIC_API_BASE_URL` | 浏览器请求基址 |
| `VITE_API_TIMEOUT` | `NEXT_PUBLIC_API_TIMEOUT` | 正整数校验 |
| `VITE_DEPLOY_ENV` | `NEXT_PUBLIC_DEPLOY_ENV` | `development`、`staging`、`production` |
| `VITE_DEFAULT_LANGUAGE` | `NEXT_PUBLIC_DEFAULT_LANGUAGE` | 当前支持值校验 |
| 无 | `SITE_URL` | 允许索引时必填的构建期绝对 HTTPS canonical 基址 |
| `API_PROXY_TARGET` | 不直接映射到客户端 | 见下方开发代理策略 |

规则：

- `NEXT_PUBLIC_*` 会编译进浏览器产物，禁止密钥、令牌、内网凭据或 Electron 私有配置。
- Next 的 `NODE_ENV` 只使用框架允许的 `development`、`test`、`production`；staging 是业务部署环境，不设置 `NODE_ENV=staging`。
- 项目环境脚本按第 10.3 节加载并校验配置后启动 Next。优先使用 Node 22 能力，不新增 `dotenv` 运行时依赖。
- `NEXT_PUBLIC_DEPLOY_ENV` 必须与脚本目标一致；production/staging 构建不能复用已污染的父进程环境。
- 未显式开启索引时允许缺少 `SITE_URL`，保持 noindex，不生成伪 canonical。production 显式开启索引时必须同时具备已确认公开名单和合法 HTTPS `SITE_URL`，任一缺失即构建失败，不静默降级。development/staging 不允许开启索引，冲突配置直接报错。
- 客户端配置只通过 `process.env.NEXT_PUBLIC_具体名称` 的静态成员访问读取，再交由共享配置校验；不能使用 `process.env[key]`、解构或先保存整个 `process.env` 来期待 Next 内联。仅构建期变量留在构建/Metadata owner，不经客户端共享配置导出。

### 10.2 `/api` 与开发代理

`output: 'export'` 不支持 Next rewrites/proxy。不能只在 `next dev` 中配置代理并让 production/Electron 静默失效。

首期按以下顺序处理：

1. 当前页面没有真实 API 时，保留 `shared/api` 的 `/api` 默认契约，但不宣称 Next 已提供代理。
2. 接入真实 Web API 前，优先由部署层和本地开发网关统一代理 `/api`；这样静态站点与 production 行为一致。
3. 如果本地直接访问后端，则在忽略的 development 环境文件中填写公开绝对 URL，并由后端明确配置 CORS。
4. Electron 接入真实 API 时使用经过确认的 HTTPS 绝对基址，不能把 `englishlearning://app/api` 当作后端。
5. `API_PROXY_TARGET` 在最终清理时删除；只有项目确实实现并测试了外部开发网关 runner 时才保留，并同步环境文档。

### 10.3 环境加载顺序与隔离

项目环境 runner 是部署环境的唯一选择入口，先确定目标，再启动 Next；不得根据当前机器碰巧存在的文件推断环境。

| 优先级（低到高） | 来源 | 约束 |
| --- | --- | --- |
| 1 | `.env` 与代码中的公开默认值 | 只放跨环境共享默认值；缺项是否可默认由逐项 schema 定义 |
| 2 | `.env.<目标环境>` | development/staging/production 只读当前目标；保留忽略的个人 `.env.development`，通过模板说明迁移 |
| 3 | `.env.<目标环境>.local` | 本地覆盖，保持 Git 忽略；CI 不依赖此文件，发现时拒绝构建以保证可重复性 |
| 4 | 显式进程注入 | 只接收 schema 白名单键；注入时必须同时提供与 runner 目标一致的 `NEXT_PUBLIC_DEPLOY_ENV`，否则报错，不静默继承 |

统一 `.env.local` 不作为项目变量的配置来源，个人配置使用带目标环境的文件。runner 只处理本项目管理的键，保留 PATH 等子进程必需环境，不通过清空全部进程环境实现隔离。

Next 仍会按 `NODE_ENV` 自动加载自己的环境文件；因此 runner 必须在启动前解析、校验并显式写入所有项目管理键，阻止 staging 的缺项被 `.env.production` 或 `.env.local` 补齐。可选空值使用 schema 认可的明确空字符串，必需值缺失直接失败；不能只校验 `NEXT_PUBLIC_DEPLOY_ENV` 一个标识。`.env`、目标文件和显式注入之间的展开/覆盖行为需写入 loader 测试，不依赖 Node 与 Next loader 的偶然差异。

必须用 development/staging/production 相互冲突的测试值覆盖配置来源、父进程污染、缺项和显式注入，检查最终客户端 bundle 与 Metadata 使用的值，而不只检查输出目录名。客户端公开值在构建时固化；修改部署环境必须重建，不能复制 production 产物后靠改环境文件变成 staging。

### 10.4 构建期数据与浏览器请求

- 当前静态参数仍来自已核实的本地模型；迁移不新增构建期后端拉取或认证流程。
- `docs/api-capability-boundaries.md` 的授权、缺项处理和请求来源/次数规则同时适用于未来构建期加载与浏览器加载，不能通过把请求移入 Server Component 扩大数据范围。
- 现有 `shared/api` 使用浏览器计时器与 URL 上下文，不得直接从 `generateStaticParams()`、Metadata 或 Server adapter 调用。未来真实需要构建期数据时，另行明确 owner、可重复构建、失败路径和依赖边界，再同步规范；不在本次预建服务端请求层。
- 静态 HTML、RSC 导航数据、JS 与公开资源都属于可下载产物。noindex 是搜索引擎策略，不是鉴权；构建时不得嵌入真实个人数据、访问令牌或仅本人可读的接口响应。

## 11. 构建、预览与产物契约

### 11.1 最终命令语义

```text
pnpm run dev                 # Next development 环境
pnpm run dev:staging         # Next dev + staging 公开配置，仅用于联调
pnpm run typecheck           # Next/TS 类型检查
pnpm run build               # lint + production Next 静态构建
pnpm run build:staging       # staging Next 静态构建
pnpm run build:production    # production Next 静态构建
pnpm run preview             # 静态服务 dist/production，不调用 next start
pnpm run desktop:dev         # Next dev + Electron
pnpm run desktop:build       # production renderer + Electron main/preload
pnpm run desktop:package     # 打包安装程序
```

不新增指向 `next start` 的 `start` 脚本。若外部平台强制要求 `start`，它只能明确等价于静态 preview，并在文档中说明，不得伪装成 Next server 部署。

### 11.2 产物整理

```text
dist/staging/       # 预发 Web 静态产物
dist/production/    # 生产 Web + Electron renderer 静态产物
dist/electron/      # Electron main/preload
release/            # Electron 安装包，不提交
```

项目脚本必须：

1. 在独立临时位置完成 Next 构建与静态导出。
2. 校验入口 HTML、所有路由 HTML、`404.html`、`/_next/static`、RSC 静态导航数据、Metadata 和 public 资源完整存在；复制完整静态导出，不以 HTML/CSS/JS 扩展名白名单筛选。
3. 校验导出环境与目标目录一致。
4. 通过同文件系统 rename 或等价策略原子替换 `dist/<environment>`，失败时不留下“部分新、部分旧”产物。
5. 不把 `.next` 缓存、开发文件或 Next server 文件复制进 Electron 包。

`pnpm run preview` 使用项目脚本提供 trailing-slash 目录解析和 404 行为，不能用一个只会回退 `index.html` 的 SPA server 掩盖导出错误。

### 11.3 RSC 导航数据与缓存

App Router 静态导出除首屏 HTML 外，还会生成供客户端导航使用的 RSC payload。其文件名、扩展名与请求形式以阶段 0 选定的 Next 版本及实际导出为准；不要把某个版本的 `.txt` 命名假定为永久契约。

- 产物清单记录 HTML、导航数据与关联资源；preview、部署层和 Electron 均按实际请求路径返回对应文件，忽略不参与文件定位的查询部分，并保留严格路径校验。
- 在固定页与动态页之间测试预取、点击、返回和刷新，检查 RSC 响应体/Content-Type、状态码与控制台；缺失 payload 必须作为资源 404，不能返回首页或 `404.html` 冒充数据。
- 带内容 hash 的静态资源才采用长期 immutable 缓存；未带 hash 的 HTML、导航数据和固定 URL Metadata/public 文件使用重新验证或短缓存策略，禁止笼统缓存所有导出文件为 immutable。
- 部署时把 HTML、RSC、关联 chunk 视为同一构建版本交付。验证旧页面仍打开时发布新产物的情况，记录 CDN 缓存刷新与旧 hash 资源保留策略；本地目录原子替换不能代替部署端一致性验收。
- 阶段 0 保存真实导航请求样例和产物映射，后续升级 Next 时复测；预览或 Electron 中意外退化为 document 导航即视为未通过。

### 11.4 TypeScript、lint 与生成文件

首期以根 `tsconfig.json` 作为 Next 和编辑器的 renderer 类型配置，将现有 `tsconfig.app.json` 的严格规则合并到根配置，移除仅服务 Vite 的项目引用和 `tsconfig.node.json`。`tsconfig.electron.json` 继续单独管理 main/preload，不将 Electron 编译范围混入 renderer。

必须同步：

- 保留 `strict`、`noImplicitReturns`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes` 等现有严格选项，适配 Next 所需 JSX、module resolution 与插件设置；不得启用 `ignoreBuildErrors` 或以框架默认配置覆盖团队类型约束。
- 移除 `vite/client` 和 `src/vite-env.d.ts`，纳入 `next-env.d.ts`、Next 路由生成类型、renderer 源码与 Next 配置；保持单元测试/Electron 的检查范围明确。
- `pnpm run typecheck` 先通过同一环境 runner 执行 Next typegen，再对根配置执行 TypeScript no-emit 检查；干净检出、从未启动 dev/build 的机器也必须通过，不依赖遗留 `.next` 类型。实际命令由 `package.json` 固化。
- 临时构建目录或自定义 `distDir` 必须与生成类型 include、`next-env.d.ts` 引用、typegen 和构建脚本一致；禁止在 typecheck 前删除它正在引用的类型文件。
- `next-env.d.ts` 由 Next 生成，不手工编辑；按选定版本的官方约定管理。`.next`、静态导出中间目录、临时构建目录、`next-env.d.ts` 与 tsbuildinfo 等生成文件纳入相应 Git/格式化/lint 排除，源码和正式契约文件继续接受检查。
- 更新 `.oxlintrc.json` 中 storage/time/clipboard/notification 的 owner overrides 到 `src/fsd`，保留原生能力只能由 owner 使用的限制；不得为迁移全局关闭规则。
- `validate-source-contracts` 同时识别 Next 适配层与 FSD 层。若采用 `@fsd/*`，解析别名后仍执行反向依赖、同层隔离与根入口检查；fixture 覆盖合法 adapter 导入以及使用相对路径/别名的非法导入，不能让别名绕过检查。
- `validate-module-docs` 区分 Next 路由约定与 FSD 公共模块；更新 README owner 清单，不机械要求每个路由目录新增业务 slice 入口。

干净检出后依次执行 typecheck、build、format/lint，并再次执行 typecheck，验证类型生成及目录清理不会相互破坏，也不会让格式化改写生成代码。

## 12. Electron 迁移

### 12.1 production 协议解析

`englishlearning://` 继续作为标准、安全自定义协议。解析规则至少覆盖：

```text
englishlearning://app/                  -> dist/production/index.html
englishlearning://app/vip/             -> dist/production/vip/index.html
englishlearning://app/profile/notes/   -> dist/production/profile/notes/index.html
englishlearning://app/_next/static/... -> dist/production/_next/static/...
```

必须保留：

- URL 解码、NUL/非法编码处理和目录穿越阻断；
- `contextIsolation: true`、`sandbox: true`、`nodeIntegration: false`；
- 具名 preload API、IPC sender 校验、拒绝新窗口与非可信导航；
- 正确 MIME type、状态码，以及第 11.3 节区分 hash 资源与 HTML/RSC 的缓存策略；
- 文件存在时只返回该文件，目录路径显式查找 `index.html`；
- 未知页面返回 `404.html`，未知 JS/CSS/图片/RSC 数据必须返回资源 404，禁止回退到 HTML；
- 按阶段 0 的真实 RSC 请求映射返回完整导出中的导航数据，覆盖查询参数、预取与客户端跳转，不只验证 `/_next/static`。

当前 `existsSync(directory)` 后直接 fetch 目录、任意缺失资源回退 `index.html` 的 SPA 行为不能保留，否则 Next chunk 404 会被伪装为 HTML 并导致白屏。

### 12.2 CSP 技术验证门

这是批量迁移前的阻断项。Next 静态 HTML 的水合脚本必须在 Electron 当前安全边界下实际运行。

按以下优先级验证：

1. 使用 production 静态导出和当前严格 `script-src 'self'` 做最小水合 PoC。
2. 若需要严格 hash/SRI，验证选定 Next 版本及 bundler 的 experimental SRI 是否覆盖本项目导出形态，并固定 bundler 与构建断言。Next.js 16.2 已加入 Turbopack SRI 支持，不预设只能使用 webpack；具体兼容性仍以 production 静态产物和 Electron PoC 为准。
3. 若仍有确定的内联脚本，为每个导出 HTML 生成可复现的 CSP hash manifest，由协议层按文档返回对应策略，并测试篡改/漏 hash 失败路径。
4. nonce 需要每请求动态渲染，不适用于本项目静态导出，不能作为首期方案。
5. 不默认加入 `'unsafe-inline'`。若安全评审明确接受临时放宽，必须单独 ADR、限定 production/dev 差异并记录关闭条件。

主题 bootstrap、Next 水合、页面切换、GSAP/OGL 和动态 import 必须一起验证。PoC 未通过时停止批量路由迁移，先修正架构选择。

### 12.3 development

`desktop:dev` 调整为：

1. 构建或 watch Electron main/preload。
2. 在 `127.0.0.1` 启动 Next dev server。
3. 由脚本选择/确认端口并做 HTTP readiness 探测，不依赖脆弱的控制台文案解析。
4. 通过 `DESKTOP_RENDERER_URL` 启动 Electron。
5. 任一子进程结束时清理其他进程，SIGINT/SIGTERM 均可退出。

开发 CSP 与 production CSP 分开验证；开发工具需要的 `unsafe-eval` 或 WebSocket 不能泄漏到 production 协议策略。

## 17. 实施前仍需确认的产品/部署项

这些事项不改变 Next 全量迁移方向，但会影响最终发布配置：

1. 允许搜索引擎索引的最终路由名单。
2. 未知路由使用标准 404，还是继续自动回首页。
3. Web 正式域名、静态托管/CDN、canonical 基址和 `/api` 网关方式。
4. Electron 正式品牌名、app ID、图标、签名、notarization 和自动更新方案。

技术实施默认值：在以上事项确认前全站 noindex；不伪造 canonical；保留现有未知路径行为；不接入真实 API 或正式桌面发布配置。

## 18. 回滚与协作策略

- 迁移使用独立分支或 worktree，迁移前保留通过验证的 Vite 基线提交。
- 阶段 1 可以让 Vite 继续作为唯一基线入口；阶段 2 切换后，目标分支只允许 Next 作为默认入口。
- 不用两个 Router 同时接管页面，不在业务组件中加入 `if (vite)` / `if (next)` 分支。
- 默认命令、CI、产物整理和 Electron Builder 在同一切换批次中更新。
- 若切换失败，整体回到基线提交或 worktree；不手工删除一半配置来“临时恢复”。
- 同一工作区的目录搬迁、路由改造和文档同步只允许一个写入 Agent；review 保持只读。

## 19. 主要风险与缓解

| 风险 | 影响 | 强制缓解 |
| --- | --- | --- |
| `src/pages` 被 Next 识别 | 构建直接失败或意外启用 Pages Router | 六层整体移动到 `src/fsd`，lint 阻断新的 `src/pages` |
| 静态导入类型变化 | TypeScript 错误、图片失效 | 97 条位图清单、模型边界 `.src` 转换、导出资源断言 |
| 动态路由漏生成 | 深链/刷新 404 | owner 公共枚举器、路由集合测试、产物 HTML 清单 |
| `useSearchParams` 破坏静态构建 | build 失败或整页 CSR | 最近 `Suspense`、查询状态专项构建测试 |
| 水合不一致 | 闪烁、交互失效 | 确定性首屏、最小 Client 边界、浏览器 API 延后 |
| 普通函数跨 Server/Client 边界或枚举器进入 Client 图 | 构建失败、静态参数不可执行 | 可序列化 props、FSD app Client 装配、无指令的混合公共入口及真实构建验证 |
| Electron 严格 CSP 阻断 Next | 桌面白屏 | 阶段 0 production PoC，SRI/hash 方案先行，不默认 unsafe-inline |
| 缺失 chunk 回退 HTML | MIME 错误、随机白屏 | 资源严格 404，只有目录路由解析 index.html |
| RSC 导航数据遗漏或跨版本缓存 | 直达正常但站内导航失败/退化 | 完整导出、payload 映射、预取/点击冒烟及 HTML/RSC/资源版本一致交付 |
| staging/production 混用 | 错误 API/SEO/品牌配置 | 独立环境 loader、匹配校验、原子产物目录 |
| 类型生成、lint owner 或别名规则遗漏 | 干净 CI 失败或边界检查失效 | 根 Next tsconfig、typegen、owner 路径/别名 fixture、生成目录排除 |
| 路由 API 替换后行为变化 | 高亮、返回状态、滚动回归 | 第 6.6 节行为矩阵和迁移前基线对照 |
| Skills 与现行规范仍指向 Vite | 后续任务恢复旧入口或误用 RSC | 第 20 节分阶段同步，四个 Skills 与治理文档一起审查 |
| 开发代理只在 Next dev 可用 | production/Electron 请求失败 | 外部同源网关或明确绝对 API URL，不使用静态 export 不支持的 rewrite |
| 迁移时顺带重构业务 | 范围和回归失控 | route adapter 保持薄层，视觉/业务变更另立任务 |
| 静态导出被误当完整 Next server | 引入不可部署能力 | 文档、lint、CI 明确禁止首期不支持特性 |
| 私有页被索引 | 数据与隐私风险 | 默认 noindex、公开名单、页面级 Metadata 与产物检查 |

### 20.4 历史 ADR 与零残留范围

- 新增迁移 ADR 记录 App Router + 静态导出、目录划分、路径函数装配、Electron CSP 和验证证据，说明哪些旧决策被替代。

- 其他涉及 Vite、SPA Router、目录或构建的旧 ADR 同样逐项标注仍有效与已替代部分；只替代失效决策，不取消仍适用的 FSD、响应式、主题或安全规则。
- 零残留脚本只阻断现行源码/配置/脚本和有效规范中的旧入口或旧指令。迁移文档、已标记的历史 ADR、反例 fixture 中的旧名称属于解释或验证数据，范围应明确且可审查，不能以全仓关键词为零代替迁移完成。
